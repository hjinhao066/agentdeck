# 队长交接（Relay handoff）

队长换席位（Relay）、清空上下文或 AgentDeck 重启后，接任的队长靠两样东西接续：
`briefing`（稳定规则，见 `main-core.js` 的 `instructions()`）和交接（动态状态）。
本页说明交接从哪里来、里面是什么、哪些事由程序保证。

## 文件，各有主人

| 文件 | 谁写 | 内容 |
|---|---|---|
| `~/.agents/boards/agentdeck-captain-handoff.md` | 程序。每次整份重写，不要手改 | 总览：一页「目录」，有硬上限 |
| `~/.agents/boards/agentdeck-captain-handoff/` 里的 7 个文件 | 程序。每次整份重写 | 按需读的细节，见下面「正文」 |
| `~/.agents/boards/agentdeck-captain-decisions.md` | 队长。程序只读，首次生成交接时放一份空模板 | 当前目标、授权范围、暂停/取消、有效决定、交付状态、等用户决定 |
| `~/.agents/memory/about-user.md` | 别处生成，程序只读 | 「你服务的人」。不存在就整节省略，不报错 |

程序不理解用户的话，所以「有效决定」由队长整理成一条一行，原话留指针。交接只引用这份文件的一部分（见「决定文件怎么引用」），
标出它的最后修改时间；在那之后的用户消息会标「未整理」。程序不改这份文件的内容和格式。
两份文件来自不同时刻时，各自的时间都写在正文里。

## 什么时候生成

- 席位 Relay：旧队长的终端被关掉之前，先存完整对话，再写交接（`seats:checkpoint`）。写不成功就不切换。
- 队长运行 `node "$AGENTDECK_BOARD_CLI" handoff`：按当前实况重新生成，返回正文并刷新文件（`seats:handoff`）。
  只读：不开会话、不动卡片、不消费回执。重启、清空上下文后以及接手核对完都用它。

生成逻辑在 `relay-handoff-core.js`（纯函数）。渲染进程给出派活记录、会话实况、未读回执、排队和最近用户消息
（`MainSession.handoffSnapshot`），主进程补上任务看板卡片和有效决定文件（`claude-seats-main.js` 的 `handoff()`）。
看板读不出来时正文里明说，只列派活记录。

## 正文：一页总览加分文件

底层逻辑是按需查询：新队长先读总览，再按目录挑要读的分文件，不用一次读完。

总览（默认不超过 6000 字，`config.captainHandoffOverview`，设置 → 队长交接里改，3000–20000）按有用程度排：

0. 你服务的人：`~/.agents/memory/about-user.md` 原样引用（逐行加 `> `），最多 2000 字，写明文件修改时间；
   超过 14 天没更新标「可能过期」；超过 2000 字只引开头并写明全文在哪。文件不存在或为空就整节省略。
1. 用户最近的原话：最新的在最前，最新一条摘录最长；每条带 `read --id … --find …` 指针。
2. 在跑的会话和等队长处理的事：一行「数一数」（未完成任务各状态条数、队员提问、未读回执、已取走未确认、矛盾、等队长拍板、等用户决定），
   再列在跑会话、提问、回执、返工、矛盾，和启动方式。
3. 用户点名的高优先级（有才有这一节）。
4. 现行有效的决定：暂停/取消/暂不启动（生效中，每条都在）、标了「长期」的条目、按时间最新的 3 条目标/授权/决定、最新一条交付状态；
   其余只给条数。
5. 目录：每份分文件写明名字、字数、是什么、什么时候读。

分文件（放在交接文件旁边的 `agentdeck-captain-handoff/` 目录，不受上限限制）：

| 文件 | 内容 | 什么时候读 |
|---|---|---|
| `tasks.md` | 未完成任务全表：每张卡的状态、验收、会话、结果、阻塞、下一步、旧轮次；高优先级带 `【高优先级】` 排在同组最前 | 要派活或查某张卡时 |
| `waiting.md` | 未读回执、已取走未确认的回执、队员提问、等队长拍板 | 处理提问和回执之前 |
| `needs-user.md` | 等用户决定清单（队长在决定文件里记的） | 向用户汇报之前 |
| `delivery.md` | 交付状态：本机版本、队长记录的最近 10 条、未完成任务提到的分支/提交/产物（队员自述，待核实） | 谈到版本、合并、打包、安装之前 |
| `decisions-history.md` | 决定文件里每一条的一行标题和它在原文件的行号；暂停项全文 | 拿不准某事是否被授权、叫停或取代时 |
| `user-messages.md` | 更早的用户消息摘录 | 总览里的原话不够时 |
| `playbook.md` | 元信息、启动方式、核对顺序、证据索引 | 刚接班时 |

总览和分文件出自同一份推导结果，计数与行数一致。

启动方式按同一份结果给出五种之一：有生效中的暂停项；有已授权待办（核对后续接）；
有会话在跑却没有任务记录（先 peek 核实，不报告就绪）；只剩待执行卡或被叫停的任务（不重启、不凑数立项）；
什么都没有（简短报告就绪）。

### 决定文件怎么引用

只引用最近一段和明确标为长期有效的条目，更早的只给指针，不原样全贴：

- 「最近」按条目开头的时间（`[10-06 12:15 …`）排，取最新 3 条（目标、授权、决定合在一起）；开头没有时间的条目算最旧。
- 「长期」：条目开头 80 字内出现「长期」二字（如 `【长期】`、`长期有效`）。
- 暂停/取消/暂不启动的条目全部在总览里，放不下时总览只给条数，全文在 `decisions-history.md`。
- 标题含「现场」的节（如「暂停时的现场」）是某一刻的流水，归「其他记录」，不当作暂停项。
- 其余条目在 `decisions-history.md` 里一条一行，前面的 `L数字` 是它在决定文件里的行号，每节最多列 30–60 条，更早的直接读原文件。

## 四种状态分开

- 会话状态：运行中、已结束、被中断（队长叫停、重启续接中、额度等待）。来自终端实况和该会话最后一条有效派活记录。
- 任务状态：待执行、执行中、待验收、返工、暂停。来自卡片的 `status`、`flag`、绑定和执行轮次。
- 验收结论：未验收、通过、不通过、结论不明确。来自卡片的审查字段和审查会话回执的开头，不看会话是否结束。
- 交付阶段：提交、合并、打包、安装。程序只确认本机运行的版本，其余以队长记录和实况为准。

会话结束不等于任务完成：

- 队长手动开的审查会话绑定在待验收的卡上，回执以「不通过」开头时，卡片回到进行中并记一次返工，不再置完成（`task-board.js` 的 `event()`）。
- 审查会话有自己的卡、用 `--reviews` 指向执行会话时，看板不知道结论。交接按派活记录把结论连回被审的卡：
  之后没有返工记录就标「返工」；卡片却是完成时标「矛盾」，要求先核实。
- 被队长 `stop` 或 `archive` 叫停的任务标「暂停（已被队长叫停）」，不列入接手。
- 卡片绑定的会话已经不在、或进行中却没有执行会话，标「没有有效执行者」并列出矛盾。

## 长度预算

总览有硬上限（默认 6000 字）；分文件不设上限。超出时按固定顺序逐步缩短，前面的先缩，用户最近的原话最后才动：
最近的决定 → 长期有效的决定 → 最新交付状态 → 「你服务的人」只引开头 → 在跑会话名单 → 提问/回执/返工/矛盾的明细行 →
高优先级明细行 → 暂停项明细行 → 「你服务的人」再缩直至只留指针 → 用户原话（8 条 → 5 → 3 → 2 → 只剩最新 1 条）。
「数一数」一行、目录和每个指针任何一步都不删：未完成任务、未答提问、未读回执、暂停/取消项，缩短后只是从总览移到分文件，
总览仍给条数和去哪读。页尾写明缩短了什么。待处理的回执在 `waiting.md` 不设条数上限：前 40 条带内容摘要，
其余只列会话和标题，写明用 `read --id 会话id` 查内容，一条都不省。

## 程序保证的去重

- 同一张卡只有一个执行者：卡片有未结束的执行轮次时，`new --task-id` 被 `bind()` 拒绝。
- 旧轮次的回执改不了卡片：会话或轮次不匹配、重复事件、已关闭轮次的事件都被忽略。
- 旧队长不能再派活：Relay 关掉旧终端时令牌作废，渲染进程按当前队长列校验调用者。
- 只有一个回执监听：`receipts --wait` 每个进程带自己的标识；同一终端里更晚启动且还在轮询的监听接管，
  更早的那个下次轮询收到一行说明后退出。停止轮询超过 15 秒的不算。
- 超时的命令不会迟到执行：`new`、`tell`、`stop`、`archive`、`answer` 的请求带 CLI 的等待期限，
  过了期限才轮到的直接拒绝，重发不会开出第二个会话。
- 回执不重复投递也不静默丢失：后台通道取走之后，队长没有再开始并完成过一轮工作的回执，Relay 和重启时不再投递，
  改为列在交接的 `waiting.md`（总览给条数），保留到下一次 Relay。接任的队长一轮工作都没做完就又被换下（额度用尽、没开工）时，
  这些回执连同它自己取走的一起带给再下一任，直到有一任队长在它们列出之后完整做完一轮。
  手动清空上下文时只重发这一类和还没取走的，已经处理过的不再发第二遍。

## 上限与窗口

交接路径上带上限的地方只有下面这些，没有一处会让一条待处理的回执或一个未结束的任务消失：

- 回执是否「已被后台通道取走」记在回执本身（`viaChannel`、`takenAt`），随 `mainSession` 保存。
  `receiptsSeen` 只是最近 500 个已返回 id 的历史，只用来认老版本取走、没有标记的回执；
  它被裁剪不影响仍在 `inflight` 或 `handoffCarry` 里的回执怎么分类。
- `pending`、`inflight`、`handoffCarry` 都不设上限；写交接时原样传入。
- 派活记录超过 120 条时只淘汰最旧的已结束记录；未结束的、结果还没写进看板的从不淘汰。
  记录到达上限时 `playbook.md` 写明：更早的旧轮次和只记在派活记录里的外部审查结论不在快照里，以看板卡片为准。
- 窗口都自己写明：用户消息只摘最近 12 条并说明更早的没有统计；每张卡的分支、提交、产物超出时写「还有没列出的」；
  接任说明只列 20 件在跑的活并写明另有几件；有效决定文件超过 512KB 时写明没有读，不当成「无记录」。

## 仍然靠队长的部分

- 用户口头说的暂停、取消、授权范围，要队长记进有效决定文件，程序才看得到。程序没有全局的「停止派活」开关。
- 没挂卡的派活没有卡片可以挡重复，只靠上面的超时保护和交接里的「不要另开」。
- 交付阶段里只有本机运行版本是程序确认的。
