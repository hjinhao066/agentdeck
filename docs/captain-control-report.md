# 队长会话控制与输入队列核查

核查日期：2026-10-03。分支：`feat/captain-stop-archive`。

## 本次行为

- `stop --id <会话id>`：向指定队员发送 Esc，取消 AgentDeck 中尚未送达的补充指令，保留终端、会话和历史。这是中断请求，不承诺 CLI 内的后台任务也会停止。
- `archive --id <会话id>`：显式结束指定终端并归档，保留历史及终端回放，不弹确认框。普通点击、自动归档仍保护忙碌会话。两条命令仅队长可以调用，不能操作队长自己；未知 id 不会影响其他会话。
- Claude 用量等待页显示「额度用尽/等待」，不计作完成，不自动投递补充指令，保留并发槽位。额度重置并恢复输出后重新显示工作状态。
- 同一会话的未发送指令显示「待补充」，按到达顺序以空行连接成一个消息，附一次任务约定并按一次 Enter；合并的旧卡片指向最后一张卡片的结果。「排队」仅表示新会话等待并发槽位。
- `tell --to <会话id> --message "指令" --replace`：取消此前尚未送达的补充，只保留新指令。`--now`：先发送 Esc，再在输入框就绪后投递；保留已有补充并一起合并。`--replace --now`：取消旧补充、中断当前操作、投递新指令。输入框里有用户未发送的文字时仍等待，避免替用户发出草稿。
- 回执只读取最终回答最后的真实【回执】/【提问】块，忽略任务约定占位、行内引用和代码示例。Claude 的工作提示及原生消息队列提示持续存在时，不因屏幕静默而发送「已停下」。

## Claude Code 自己的排队：批量进入同一次处理，不是逐条任务串行

依据：[Claude Code 官方交互文档](https://code.claude.com/docs/en/interactive-mode#when-claude-code-sends-what-you-queued)，以及本机安装的 **2.1.288** 内嵌实现的只读检查。

官方文档说明，普通排队文本可能在工具调用完成时进入当前轮；剩余消息会在轮结束时按输入顺序自动送出。斜杠命令、`!` shell 命令另有逐条处理路径。因此不能把 Claude 的「queued messages」理解成每条指令完成后才开始下一条任务。

本机实现里，`ttt` 通过 `dequeueAllMatching` 收集符合条件的普通队列项，交给一次 `executeQueuedInput`。`_Ze` 将该批各项转换为消息并收集到 `Qo`，然后调用一次 `ht(Qo, …)` 执行模型处理。**这是合批进入同一次处理；内部可保留多个消息条目，不能据此声称总是拼接成一个字符串。** 命令、IDE 选区、提交 hook 的筛选状态等会分批；结论适用于普通文本队列，不保证所有队列项都无条件一次清空。

没有启动真实 Claude 对话或用真实模型消费测试额度；以上是官方说明和本机实现证据，不是线上行为实测。

AgentDeck 的补充队列本次明确在应用层连接成**一个文本消息、一个 turn**再投递，不依赖各 CLI 自己如何处理原生队列。
